# План доработок: схемы процессов, уточнения, багфикс, проработка задачи

Составлен 2026-10-13 по итогам разбора Spec Kit ([research/spec-kit.md](research/spec-kit.md)), решения по спорным вопросам приняты в тот же день (раздел 4). Документ рабочий: по мере выполнения каждого этапа его решения переносятся в [design.md](design.md), а здесь остаётся статус. Правила из CLAUDE.md действуют: хосты равноправны, тексты для агентов и схемы живут в `assets/`, ядро детерминировано, тесты вместе с кодом, версию и публикацию меняет владелец.

## 1. Цели

1. **Команда clarify.** Отдельный шаг уточнения запроса до планирования: роль задаёт ограниченное число вопросов с вариантами и рекомендацией, человек отвечает по одному в чате хоста или пакетом в CLI, ответы фиксируются в артефакте и доходят до всех следующих ролей. В headless-режиме вопросы останавливают запуск так же, как сегодня P0, а в будущем публикуются в комментарии тикета или пул-реквеста.
2. **Несколько схем процесса.** Кроме текущего процесса фичи появляются две схемы: **проработка задачи** (на выходе бриф, достаточный для автономного выполнения) и **сокращённый багфикс**. Схема выбирается при создании изменения, проект может добавить свою.

Не входит в план: задачи сходимости, чеклист challenger с флажками, хуки фаз, манифесты материалов хоста, хост `generic` (кандидаты D–K из разбора). Они не нужны для целей выше и обсуждаются после.

## 2. Целевая картина

### Схемы

| Схема | Фазы | Гейты (supervised / checkpoint) | Результат |
|---|---|---|---|
| `feature` (сегодняшняя, по умолчанию) | research → **clarify** → propose → [proposal] → plan → [plan] → challenge → cover → tests_review → [tests] → implement → verify → review → deliver | proposal, plan, tests / plan | Пул-реквест |
| `bugfix` | rca → [rca] → fix → verify → review → deliver | rca / rca | Пул-реквест с исправлением, RED-оракулом и отчётом верификатора |
| `discovery` | research → clarify → brief → [brief] → challenge → done | brief / brief | `brief.md`, дельты `specs/`, `decisions.md`; продолжение в схеме `feature` на месте |

Профиль `autonomous` отключает все гейты схемы; вопросы P0 останавливают при любом профиле, P1 только там, где включён гейт следующей фазы, P2 никогда (правила раздела 8 design.md не меняются).

Схема хранится в `change.yaml` (`schema: feature`, отсутствие поля означает `feature`), файл схемы `assets/schema/<имя>.yaml` описывает фазы (роль, профиль модели по желанию, гейт с профилями автономии, артефакты, именованные проверки, файл evidence, цель запуска, инструкция фазы), цели возврата по категории блокера и артефакты с инструкциями, как сегодня `default.yaml`. Проект переопределяет схему файлом `.sbox/schema/<имя>.yaml`. Роли не добавляются: новые фазы выполняют planner, implementer, verifier, reviewer, challenger, researcher; материалы хостов (агенты) не меняются.

### Механизм вопросов (общий для всех схем)

- Блок `sbox-result` планировщика расширяется: `questions: [{ id, priority: P0|P1|P2, category, text, why, options: [{ id, text, impact }], recommended, rationale }]`. Проверки при `report`: не больше `limits.questionsPerRound` (по умолчанию 5), у P1 и P2 обязательна рекомендация, идентификаторы уникальны.
- CLI решает судьбу вопросов детерминированно: P2 принимаются по рекомендации сразу, P1 принимаются, если ближайший гейт выключен, иначе ждут человека; P0 ждут всегда. Открытые вопросы переводят изменение в `waiting_user`, `sbox next` отвечает `kind: questions`.
- `sbox answer --change <id> Q1=B Q2="свой ответ" Q3=recommended [--by]` записывает ответы, дописывает `clarifications.md` (сессия по дате, вопрос → ответ, кто и откуда ответил, принятые рекомендации), и продолжает изменение: завершает фазу clarify или возвращает в фазу, где вопросы возникли.
- `sbox clarify --change <id> [--focus "<тема>"]` запрашивает дополнительный круг уточнений из фаз propose и plan (и с ожидающего гейта: гейт сбрасывается и повторяется после круга).
- `clarifications.md` пишет только CLI; в пакете он идёт полем `files.clarifications` с ограничением для ролей: уточнения это решения человека, они уточняют запрос и сильнее evidence; противоречие с ними это блокер категории «артефакт».
- Скилл `sbox-run` получает шаг `questions`: показать один вопрос с рекомендацией, принять «да» как рекомендацию, собрать ответы, вызвать `sbox answer`, снова `next`. Новый скилл `sbox-clarify` («уточни задачу») вызывает `sbox clarify` и тот же цикл. Оба устанавливаются в Claude Code и Codex из `assets/skills` без изменений; headless получает те же ответы через `sbox answer`.
- **Асинхронные каналы (сценарий на будущее, учитывается в модели данных сейчас).** Вопросы хранятся в `change.yaml` в форме, пригодной для публикации одним сообщением в комментарий тикета или пул-реквеста: идентификатор, текст, варианты, рекомендация, приоритет, `posted_at` по каналу. Ответы читаются из комментариев вида `/sbox answer Q1=B Q2=recommended` теми же адаптерами каналов, что и решения гейтов (`pr-comments`, позже `tracker`), с записью автора и канала ответа. Это расширение `GateChannel` из раздела 11 design.md (`post` публикует и гейт, и вопросы; `read` разбирает и approve/reject, и answer); реализуется вместе с каналами, в этот план входит только совместимая модель данных и команда `answer`.

## 3. Этапы

Порядок: сначала схема процесса как данные (решение 1), чтобы clarify, bugfix и discovery описывались в YAML один раз; затем clarify, багфикс, проработка задачи.

### Этап 1. Схема процесса как данные

Размер: большой. Поведение схемы `feature` не меняется, это условие приёмки.

| Область | Изменения |
|---|---|
| Данные | `assets/schema/default.yaml` → `assets/schema/feature.yaml` с разделом `phases` (id, role, profile по желанию, objective, instruction, gate с профилями автономии, artifacts, checks, evidence, after-действия `protect` и `seal`, `binds`), `returns` по категориям блокера; артефакты и `apply` как сегодня. Переопределение проекта `.sbox/schema/<имя>.yaml`, старое `.sbox/schema/default.yaml` читается как `feature`. Тема справки `schema`. |
| Ядро | `schema.ts`: загрузка схемы по имени, валидация (роли известны, гейты уникальны, цели возврата существуют, профили допустимы). `phases.ts`: порядок фаз, роль, гейт и возвраты берутся из схемы изменения, типы `Phase` и `Gate` становятся строками с проверкой по схеме. `report.ts`: `checkPhaseDone` как диспетчер именованных проверок (request_map, deviations, artifacts, deltas, findings_required, tasks_done, protected, drift, wiring, dispositions, narrative) и after-действий. `packet.ts`: цели запуска и инструкция фазы из схемы. `model-policy.ts`: профиль фазы между явным `runner.roleProfiles` и дефолтом роли. `deliver.ts`: чеклист готовности строится по артефактам и фазам схемы. `change.ts`: поле `schema`. |
| CLI | `change new --schema <имя>`, `change list` и `status` показывают схему, `sbox schema list|show <имя> --json`. |
| Документация | design.md: новый раздел «Схемы процессов», правки разделов 4, 6, 12, 18 (профиль фазы); README «Что где лежит». |
| Тесты | Тест эквивалентности: встроенная `feature.yaml` даёт те же константы, что прежний код; все существующие тесты проходят без изменения смысла; валидация схемы, проектное переопределение, профиль фазы. |

Готово, когда: `vitest` зелёный, `sbox schema show feature` печатает фазы, старые изменения без поля `schema` продолжают работать.

### Этап 2. Уточнения (clarify)

Размер: средний.

| Область | Изменения |
|---|---|
| Данные | `feature.yaml`: фаза `clarify` после `research` (роль planner, профиль роли, то есть complex), инструкция фазы: таксономия категорий (объём и границы, модель данных, сценарии и UX, нефункциональные требования, интеграции, краевые случаи и ошибки, ограничения, терминология, критерии завершения), лимит, формат вопроса с вариантами и рекомендацией. `assets/roles/planner.md`: раздел «Фаза clarify» (найти развилки, которые запрос и evidence не закрывают; не спрашивать о том, у чего есть разумное умолчание, а записать его допущением; вопросы с рекомендацией). `assets/help/result.md`: поля вопросов. `assets/skills/sbox-run.md`: шаг `questions`. Новый `assets/skills/sbox-clarify.md`. |
| Ядро | `change.ts`: модель вопроса с вариантами, статусом, ответом и отметками публикации; поле `clarify` (включён ли шаг, фаза возврата); счётчики вопросов в `interventions`. `result.ts`: разбор расширенных вопросов. `report.ts`: проверки вопросов, автоприём по правилам P, перевод в `waiting_user`, запись `evidence/clarify-N.md`. `phases.ts`: пропуск фазы по флагу изменения, возврат из круга уточнений в исходную фазу. Новый `clarifications.ts`: запись файла. `packet.ts`: `files.clarifications`, ограничение. `gates.ts`: разбор `/sbox answer` в комментариях (минимальная поддержка канала `pr-comments`). |
| CLI | `sbox answer`, `sbox clarify`, `next` с `kind: questions`, `status` с открытыми вопросами, `change new --no-clarify`, конфиг `process.clarify` (по умолчанию включён) и `limits.questionsPerRound` (по умолчанию 5). |
| Документация | design.md: раздел 4 (таблица фаз, схема состояний), раздел 5 (блок ответа), раздел 8 (вопросы: единая модель для clarify и plan), раздел 11 (каналы: вопросы), раздел 12 (команды). README, pilot.md. |
| Тесты | Разбор блока, проверки `report`, автоприём по профилям, `answer` (переходы состояния, содержимое `clarifications.md`), `clarify` из propose/plan и с гейта, `next` с вопросами, разбор ответа из комментария, сквозной тест на фикстуре, тексты скиллов в тестах хостов. |

Готово, когда: изменение на фикстуре проходит research → clarify с двумя вопросами → `answer` → propose без участия модели; в профиле `autonomous` P1 и P2 принимаются автоматически и видны в `clarifications.md`; `sbox host install` для обоих хостов кладёт `sbox-clarify`.

### Этап 3. Схема `bugfix`

Размер: средний. Основа: раздел «Вариант схемы для багфиксов» design.md и RCA-контракт из Suite. Сокращение против полной схемы: нет исследователя, тестировщика, аудита плана и ревью тестов; четыре запуска ролей на успешный прогон (решение 3).

| Область | Изменения |
|---|---|
| Данные | `assets/schema/bugfix.yaml`: фазы `rca` (planner; артефакт `rca.md`, дельта `specs/` пропускаемая; гейт `rca`), `fix` (implementer; проверка `protected` не применяется, after `seal`), `verify` (verifier; `drift`, `binds`), `review` (reviewer; `drift`, `dispositions`, `narrative`, `binds`), `deliver`; возвраты: артефакт → rca, тесты → fix, реализация → fix. Шаблон и инструкция `rca.md`: триггер и предусловия, наблюдаемое и ожидаемое, первое расхождение, нарушенный инвариант и владелец, цепочка причин с доказательствами `путь#символ`, сильнейшая альтернатива и чем отвергнута, границы правки и что сохранить, оракул Given / When / RED / PASS, риски; `skip_specs: true` по умолчанию, иначе дельта с добавленным сценарием. Роли: planner «Фаза rca», implementer «Фаза fix» (сначала RED-тест по оракулу и наблюдение падения, затем минимальная правка у владельца инварианта, GREEN, регрессия, проверка ближайшего неверного варианта), verifier «Багфикс» (оракул на базовой ревизии падает, на итоговой проходит; размер правки в границах контракта). |
| Ядро | Проверка `rca_contract` (обязательные разделы и оракул), `deliver` без пунктов о tasks и coverage для этой схемы, `sbox changeset baseline --change <id>` создаёт отдельную рабочую копию базовой ревизии под `~/.sbox/worktrees/<изменение>/base` для прогона оракула верификатором (полезно и схеме `feature`). |
| CLI | `sbox change new <id> --schema bugfix --request "<отчёт или ссылка>"`; размер по умолчанию `small`. |
| Документация | design.md раздел 4 (вариант bugfix сверяется с реализацией), раздел 12, README, pilot.md (как завести баг). |
| Тесты | Сквозной прогон на фикстуре: rca → гейт → fix → verify (с baseline) → review → archive, с `skip_specs` и с добавленным сценарием; возврат «тесты» из verify в fix; чеклист доставки без tasks/coverage. |

Готово, когда: баг на фикстуре доходит до архива за четыре отчёта ролей, в описании пул-реквеста есть оракул и результат верификации на базе и на итоге.

### Этап 4. Схема `discovery` (проработка задачи)

Размер: средний или большой. Основа: раздел 9 design.md; из Spec Kit берутся таблица оценки и явный вердикт. Дискавери хранится как изменение со схемой `discovery` в `.sbox/changes/` (решение 4), продолжение на месте (решение 5).

| Область | Изменения |
|---|---|
| Данные | `assets/schema/discovery.yaml`: `research` → `clarify` (несколько кругов) → `brief` (planner; артефакты `brief.md`, `specs/` пропускаемая, `decisions.md`; гейт `brief`) → `challenge` (challenger в режиме достаточности) → `done`; возвраты: артефакт → brief. Шаблон `brief.md` по разделу 9 плюс таблица оценки (обоснованность проблемы, сила доказательств, ценность против бездействия, реализуемость, риски: strong / adequate / weak / unknown) и чеклист достаточности из восьми критериев. Роли: planner «Фаза brief», challenger «Достаточность брифа» с вердиктом `достаточно` / `доработать` / `не делать` (последний это блокер «пользователь» с причиной: остановка это нормальный исход). Исследование обязано искать доказательства против идеи. |
| Ядро | Детерминированная проверка достаточности: нет открытых P0 и P1, capability дельт есть в истине или помечены новыми, дельты валидны, нет пересечения по capability с активными изменениями, вердикт challenger записан. Передача: `sbox discover handoff <slug>` переключает то же изменение на схему `feature` с фазы `plan`: гейт proposal считается пройденным брифом, clarify пропущен, профиль `autonomous` (переопределяется флагом); бриф и решения попадают в пакет планировщика как источник proposal и раздела «Решения». `resolveChange` без `--change` учитывает схему при выборе единственного активного изменения. |
| CLI | `sbox discover new <slug> --request|--file|--tracker`, `sbox discover validate <slug>`, `sbox discover handoff <slug> [--autonomy]`, `sbox change close <id> --reason` для вердикта «не делать». Позже, отдельным шагом: `sbox change new --from-brief <файл|slug>` для брифа, сделанного вне репозитория. |
| Документация | design.md раздел 9 переписывается под схему (папка `.sbox/discovery/` исключается из раскладки), разделы 6 и 12, этап 3 плана; README и pilot.md (сценарий «проработать задачу и запустить автономно»). |
| Тесты | Сквозной прогон: research → clarify (два круга) → brief → гейт → challenge «достаточно» → handoff → plan в схеме feature без гейтов; `validate` ловит открытый P1 и пересечение capability; вердикт «не делать» закрывает изменение. |

Готово, когда: на фикстуре задача доходит до брифа с ответами на вопросы, после `handoff` цикл `feature` стартует с `plan` и идёт до архива без гейтов.

## 4. Принятые решения (2026-10-13)

| # | Вопрос | Решение |
|---|---|---|
| 1 | Порядок этапов | Сначала схема процесса как данные, затем clarify, bugfix, discovery |
| 2 | Clarify по умолчанию в схеме `feature` | Включён; выключается флагом `--no-clarify`, конфигом `process.clarify` и автоматически после `handoff` |
| 3 | Кто пишет RED-тест в багфиксе | Реализатор в фазе `fix`; независимость даёт верификатор на базовой ревизии; четыре запуска ролей |
| 4 | Где живёт проработка задачи | Изменение со схемой `discovery` в `.sbox/changes/`; модель вопросов и ответов проектируется под асинхронные каналы (комментарии тикета и пул-реквеста), доставка в каналы реализуется вместе с каналами гейтов |
| 5 | Продолжение после брифа | `handoff` на месте в этапе 4; импорт чужого брифа `--from-brief` позже |
| 6 | Лимит вопросов на круг | 5, настройка `limits.questionsPerRound` |
| 7 | Профиль модели фазы | Схема может задавать профиль фазе (после явного `runner.roleProfiles`, до дефолта роли); фаза clarify идёт на профиле планировщика (complex) |
