# Пилот @spec-box/sdd в проекте: пошаговая инструкция

Для фиче-лида, который уже выполнил `npm install -g @spec-box/sdd` и `sbox init --host claude` в репозитории продукта. Инструкция ведёт от пустого `.sbox/` до первого пул-реквеста, готового к влитию, сначала в интерактивном режиме из Claude Code, потом в headless-режиме. Время: настройка около часа, первое изменение от пары часов до дня в зависимости от фичи.

## Шаг 0. Проверить окружение

```bash
sbox --version # 0.2.x
sbox doctor    # ошибок быть не должно, предупреждения допустимы
```

`doctor` показывает, какая аутентификация будет у среды `claude`: вход Claude Code этой машины годится для интерактивного и локального headless-режима под вашим аккаунтом, для CI нужен `ANTHROPIC_API_KEY`. Если хотите использовать Codex, добавьте в `.sbox/config.yaml`:

```yaml
runner:
  codex:
    executable: /Applications/ChatGPT.app/Contents/Resources/codex
```

## Шаг 1. Заполнить проектную документацию

Файлы в `.sbox/project/` это единственный источник знаний о проекте для ролей. Категории и обязательные разделы уже в шаблонах, `doctor` проверяет их наличие.

| Файл | На что влияет сильнее всего |
|---|---|
| `overview.md` | Понимание границ продукта исследователем и планировщиком |
| `architecture.md` | Куда планировщик и реализатор пойдут за кодом |
| `conventions.md` | Стиль кода реализатора, находки ревьюера |
| `testing.md` | Уровни тестов, команды прогона и **правило именования тестов по сценариям**: от него зависит сопоставление тестов с утверждениями спецификации |
| `workflow.md` | Ветки, обязательные проверки, что запрещено без человека |
| `glossary.md` | Формулировки утверждений в спецификациях и тестах |
| `contracts.md` | Только если есть внешние API; можно оставить шаблон |

Быстрый способ: напечатайте промпт командой `sbox prompt show project-docs` (формулировки подставляются под адаптер проекта: spec-box или OpenSpec), отправьте его в Claude Code в корне репозитория. Прочитайте результат и поправьте руками: это утверждает человек.

Спецификации. Если в проекте есть `.tms.json` и YAML spec-box, `sbox spec list` покажет их. Если нет, истина заводится в `specs/*.spec-box.yml`; можно начать с пустой истины, планировщик создаст новую capability дельтой.

Закоммитьте `.sbox/`, `.claude/`, `.gitignore` и `specs/` в репозиторий: состояние изменений живёт в файлах.

## Шаг 2. Выбрать первую фичу

Подходит небольшая фича, которая меняет поведение продукта: тогда пройдут все фазы, включая дельту спецификации и тесты до кода. Не подходит рефакторинг (нет дельты) и большая фича с несколькими контрактами (первый прогон должен быть коротким).

Создайте ветку и изменение:

```bash
git checkout -b sbox/add-greeting
sbox change new add-greeting --title "Приветствие пользователя" --request "Показывать приветствие с именем пользователя в шапке главной страницы"
sbox status
```

Ветку лучше создать до `change new`: базовая ревизия для change-set фиксируется в момент создания изменения.

## Шаг 3. Первое изменение из Claude Code

В корне репозитория откройте Claude Code и вызовите скилл:

```text
/sbox-run add-greeting
```

Скилл ведёт цикл сам: запрашивает `sbox next`, запускает субагента нужной роли, сдаёт ответ через `sbox report`, и так до гейта. Порядок фаз и остановок в профиле `supervised`:

1. **research** → исследователь пишет `evidence/research.md`.
2. **propose** → планировщик пишет `proposal.md`. **Гейт proposal**: прочитайте предложение, ответьте «да» или замечанием.
3. **plan** → дельты в `specs/`, `design.md`, `tasks.md`. **Гейт plan**: читайте в порядке `design.md` (общая картина, решения, вопросы с приоритетами), затем дельты, затем задачи. Вопросы P0 останавливают процесс до вашего ответа.
4. **cover** → тестировщик пишет тесты и `coverage.yaml`, ревьюер проверяет тесты. **Гейт tests**: посмотрите тесты и покрытие.
5. **implement** → реализатор выполняет `tasks.md`; тесты защищены от изменения. CLI запечатывает change-set.
6. **verify** → верификатор прогоняет проверки и возвращает пункты PASS/FAIL/PARTIAL и пробелы.
7. **review** → ревьюер даёт вердикт, распоряжается каждым не-PASS пунктом и пишет описание для пул-реквеста.
8. **deliver** → скилл предлагает `sbox deliver`.

Гейты можно решать и из терминала:

```bash
sbox approve plan --by <ваш логин> --answer Q1=B
sbox reject plan --comment "Сузить объём: без миграции"
```

Что смотреть между шагами:

```bash
sbox status                                      # фаза, статус, артефакты, задачи, change-set
sbox validate                                    # артефакты и дельты
sbox spec diff                                   # что меняется в истине
cat .sbox/changes/add-greeting/runs/r3/result.md # полный ответ роли
```

Если отчёт роли отклонён детерминированной проверкой (не создан артефакт, не отмечены задачи, тронут защищённый тест), скилл сам передаёт диагностику роли и повторяет запуск. После двух отклонений изменение паркуется: `sbox status` покажет причину, продолжение командой `sbox change resume add-greeting --comment "..."`.

## Шаг 4. Доставка

```bash
sbox deliver --check # чеклист готовности из девяти условий
sbox deliver         # архив, применение дельт к истине, коммит, push, пул-реквест
```

Для пул-реквеста в `.sbox/config.yaml` должно быть `repo.adapter: github`, а в окружении `GITHUB_TOKEN` с правом на репозиторий; owner и repo берутся из `origin`. С адаптером `local` команда только коммитит и пушит при наличии remote. Флаг `--keep-draft` оставит пул-реквест черновиком.

После доставки изменение лежит в `.sbox/changes/archive/<дата>-add-greeting/`, дельта уже влита в `specs/`, описание пул-реквеста собрано из вердикта ревьюера, отчёта верификатора и чеклиста.

## Шаг 5. То же самое headless

Второе изменение прогоните без Claude Code в роли оркестратора:

```bash
sbox change new add-search --title "..." --request "..."
sbox run --change add-search       # роли выполняет Claude через SDK до гейта
sbox approve proposal --by <логин> # решения гейтов из терминала
sbox run --change add-search
```

Фоновый вариант: `sbox run --change add-search --detach`, затем `sbox watch --change add-search`; журнал в `.sbox/changes/add-search/runs/run.log`. Остановка: `sbox stop --change add-search`. Лимиты на один вызов: `--max-runs N`, `--max-cost USD`; в конфиге `limits.returnsPerPhase` и `limits.rejectionsPerPhase`.

Запуск идёт под вашим входом Claude Code: это допустимо для вашей собственной работы на вашей машине; для CI и общих запусков нужен ключ API.

## Куда записывать локальные особенности проекта

Три места по характеру знания:

| Знание | Где | Когда роль это прочитает |
|---|---|---|
| Правило, которое нельзя нарушать (например, «новые модули в `src/features` повторяют структуру `src/features/export`») | `.sbox/project/decisions/ADR-NNNN-<slug>.md` с `scope` | Всегда: правила попадают в пакет планировщика, тестировщика, реализатора и ревьюера, ревьюер проверяет их явно |
| Описание области: как устроен модуль, какой образец повторять, подводные камни | `.sbox/wiki/<область>.md` с фронтматтером `summary`, `read_when`, `source_roots` (шаблон в `.sbox/wiki/README.md`) | Индекс страниц (summary и read_when) есть в каждом пакете; роль читает страницу, если read_when подходит к задаче |
| Замечание к конкретному изменению | `sbox reject plan --comment "…"` | Сразу: планировщик получает замечание как фидбэк и переделывает артефакты |

Исследователь обязан найти ближайший аналог в проекте и записать его в Evidence Pack, а планировщик заполняет в `design.md` раздел «Единообразие» с образцом и отступлениями. Если ИИ всё же предложил решение не по образцу, отклоните план с замечанием и заведите страницу wiki для этой области: следующие изменения её увидят.

## Как не платить лишнего

Наблюдения из сравнения с agentic-openspec на одной фиче (16–17 сентября): @spec-box/sdd сделал 18 запусков ролей и 1163 хода модели против 4 запусков и 240 ходов, при похожем контексте на ход. Что на это влияет и что делать:

- **Усилие задаётся в агентах.** Субагент Claude Code без поля `effort` во фронтматтере наследует усилие сессии: так в пилоте все роли работали на `xhigh`. Теперь `sbox host install` пишет в каждого агента `effort` из `runner.efforts` (по умолчанию `medium`, как у agentic-openspec). Усилие самой сессии влияет только на оркестратора; его тоже разумно держать на medium.
- **Модели по ролям.** По умолчанию агенты Claude Code получают `opus` только для planner и challenger, остальные `sonnet`; сложность «высокая» переводит implementer, tester и reviewer на pro-модель. Переопределение в `runner.models`, после правки конфига выполните `sbox host install --target claude`.
- **Каждое отклонение гейта это цикл.** Отклонение запускает доработку роли, а после тестов ещё и ИИ-ревью. Мелкие правки формулировок в артефактах вносите сами и утверждайте; неблокирующие замечания ревьюера не обязаны исправляться до утверждения. Повторное ИИ-ревью тестов после доработки по замечанию человека по умолчанию выключено (`testing.reviewReworks`).
- **Возврат к роли продолжает её сессию.** Скилл `sbox-run` переиспользует уже запущенного субагента той же роли через SendMessage, чтобы он не перечитывал проект заново.
- **Оркестратор не читает артефакты.** Скилл запрашивает `sbox next --brief` и опирается на ответ `sbox report`; полные пакеты и отчёты ролей в его контекст не попадают.
- **Артефакты короче.** Ограничения в схеме: proposal до 40 строк, design до 120, Evidence Pack до 80. Дизайн в пилоте занимал 30 КБ и читался четырнадцать раз.
- **В пул-реквест не попадают пакеты ролей.** `runs/r*/packet.json` добавлены в `.gitignore` при `sbox init`; в репозитории остаются ответ роли и receipt.

## Новый модуль подключён не везде: как это ловится

Случай из пилота: новый плагин добавлен в решение и в конфиг сборок, но не в проект хоста, поэтому сборка проходит, а при запуске плагин не загружается. Три уровня защиты:

1. Исследователь перечисляет места подключения образца: `git grep -l -F --untracked -- '<аналог>'` вне его каталога. Каждому файлу соответствует задача.
2. Планировщик пишет в `design.md` строки «Образец: `X`» и «Новый модуль: `Y`». Тогда верификатор получает в пакете список файлов, где образец зарегистрирован, а новый модуль нет, и решает по каждому: нужна регистрация (FAIL) или файл относится к другому контексту образца (PASS с обоснованием). Файлы, которые верификатор не рассмотрел, CLI добавляет в его отчёт пунктами `W1…` со статусом PARTIAL, и ревьюер обязан дать им disposition. Это подсказка, а не истина: образец может упоминаться в тестах, CI или документации, где новому модулю не место. Жёсткая ошибка `WIRING_MISSING` включается только опцией `wiring.strict: true` в конфиге. Команду можно запустить и руками: `sbox wiring --analog X --new Y`. Проектный чеклист «что подключить для нового модуля» держите на странице wiki с `read_when`: он точнее любого grep.
3. Верификатор обязан запустить приложение, если `testing.md` описывает, как это сделать, и проверить затронутый маршрут; ревьюер не принимает пробел `manual_gap_accepted` для проверки, выполнимой по `testing.md`. Поэтому в `testing.md` нужна строка про дымовой запуск: команда, зависимости, порт, URL.

## Проверка интерфейса: браузер для агентов и вход человеком

Если у продукта есть веб-интерфейс, верификатор проверяет затронутую страницу в браузере, а не только сборкой. Для этого в пакете есть отдельный бинарник `sbox-browser`.

1. `sbox-browser doctor` покажет, какой браузер будет использован: системный Chrome подходит; если браузера нет, `sbox-browser install` скачает Chrome for Testing в `~/.sbox/browser/cache`. Существующий браузер задаётся через `browser.executable` в `.sbox/config.yaml` или `SBOX_BROWSER_EXECUTABLE`.
2. В `.sbox/config.yaml` укажите `browser.baseUrl` локального запуска и, если нужен вход, `browser.profile`; в `testing.md` заполните раздел «Проверка интерфейса в браузере»: базовый URL, профиль, дымовые маршруты.
3. Вход выполняет человек один раз: `sbox-browser login https://app.local --profile app`. Откроется окно браузера, войдите и нажмите Enter в терминале (или добавьте `--until-url '*/dashboard*'`, чтобы вход завершился сам). Куки остаются в профиле `app`; остановите сессию командой `sbox-browser stop`, дальше роли работают headless под этим профилем.
4. Проверьте сами: `sbox-browser goto /orders`, `sbox-browser snapshot`, `sbox-browser console --errors`, или попросите Claude Code через скилл `/sbox-browser` («проверь страницу заказов»). Так же работает и верификатор: снимок, действия по ссылкам `[eN]`, текст, консоль, сетевые ошибки, скриншот как доказательство.
5. Для headless-запусков в CI перенесите вход файлом: `sbox-browser state save auth.json` на своей машине, в CI `sbox-browser state load auth.json` из секрета. Файл содержит куки входа: не коммитьте его.

## Метрики

```bash
sbox metrics               # все изменения, активные и архивные
sbox metrics --change <id> # одно
sbox change rate <id> --score 4 --comment "принял с одной правкой"
```

Что считается: время агентов по фазам (в интерактивном режиме от выдачи пакета до записи ответа), ожидание человека на гейтах, число запусков, стоимость (только для headless-запусков через SDK), возвраты и отклонения отчётов, вмешательства (отклонённые гейты, `resume`, вопросы к человеку, отклонённые отчёты), признак «прошло автономно» и ваша оценка результата. Сводка даёт долю автономных изменений, медианы времени и запусков, среднюю оценку.

## Шаг 6. Что записать по итогам пилота

- Где роли ошибались: какая фаза, что было в `runs/rN/result.md`, что пришлось исправлять человеком. Это материал для правки текстов ролей в `assets/roles/` или проектных переопределений в `.sbox/roles/<role>.md`.
- Каких сведений не хватило в `.sbox/project/*.md`: добавьте их туда, а не в промпты.
- Сколько запусков и какая стоимость: `runs/*/receipt.json`.
- Что мешало на гейтах: слишком много вопросов P1 или, наоборот, недостаток решений.

## Если что-то пошло не так

| Сообщение | Что делать |
|---|---|
| `CHANGE_BUSY` | Другой процесс держит `.lock`; если он мёртв, блокировка снимется сама при следующем запуске, иначе `sbox stop` |
| `REVISION_CONFLICT` | Файл `change.yaml` изменён параллельно; повторите команду |
| `PROTECTED_CHANGED` | Реализатор изменил, удалил или добавил файл под защитой: сравнение идёт по содержимому со снимком, снятым при завершении фазы cover (коммиты не нужны). Откатите тестовые файлы; спорный тест возвращается блокером «тесты» |
| `CHANGESET_DRIFT` | После запечатывания изменился код (не документация, не `.gitignore`, не материалы хостов): `sbox changeset seal` и заново verify и review. Безобидные файлы перепривязываются сами, список шаблонов в `changeset.nonInvalidating` |
| Пункт 9 чеклиста «вердикты не привязаны» | После последнего запечатывания фазы verify и review не завершались: `/sbox-run` или `sbox run` пройдут их по текущему change-set. `sbox deliver --force` доставит как есть, невыполненные пункты останутся в описании пул-реквеста |
| `NO_RESULT_BLOCK` | Ответ роли без блока `sbox-result`; скилл повторяет запуск сам, при ручном `sbox report` допишите блок |
| статус `parked` | Исчерпан бюджет возвратов: `sbox change resume <id> --returns N --comment "..."` |
| `ARCHIVE_EXISTS` | В `changes/archive/` уже есть непустой каталог с этим идентификатором и датой. Пустой след прерванной попытки (например, каталоги без файлов после `git checkout`) удаляется сам; непустой сравните с папкой изменения и удалите или переименуйте. Истина спецификаций при этой ошибке не трогается |
| `TRUTH_INVALID` | После применения дельт истина стала невалидной (дубликаты требований): изменения истины откачены, изменение осталось в папке; проверьте дельты и истину |
| статус `delivery_unknown` | Коммит или пул-реквест могли создаться: проверьте вручную, затем `sbox change resume <id>` и `sbox deliver` |
| `BROWSER_NOT_FOUND` | Браузер не найден: `sbox-browser install` или путь к существующему через `browser.executable` / `SBOX_BROWSER_EXECUTABLE` |
| `BROWSER_SESSION_HEADLESS` | `login` требует окна, а сессия уже работает headless: `sbox-browser stop` и повторите, либо другая `--session` |
| `BROWSER_START_FAILED` | Браузер не запустился: журнал в `~/.sbox/browser/logs/<сессия>.log`; профиль, открытый другим Chrome, нужно закрыть |
| `BROWSER_REF_STALE`, `BROWSER_REF_UNKNOWN` | Ссылка `[eN]` из старого снимка: сделайте `sbox-browser snapshot` заново, ссылки нумеруются при каждом снимке |
