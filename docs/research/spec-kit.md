# GitHub Spec Kit 1.1.3: разбор и сравнение с @spec-box/sdd

Источник: https://github.github.com/spec-kit/ и клон github/spec-kit в `~/projects/tmp/gh-spec-kit` (HEAD 03de6617, 2026-10-12, версия пакета 1.1.4.dev0, последний релиз 1.1.3 от 2026-10-09). Сайт документации собран из папки `docs/` репозитория (docfx, обновлён 2026-09-28), поэтому разбор сделан по исходникам. Дата разбора 2026-10-12. Код проекта не запускался.

## Что это

Spec Kit — «process harness» для кодирующих агентов: CLI `specify` (Python 3.11+, typer) создаёт в проекте папку `.specify/` и устанавливает в выбранный агент набор команд-скиллов, которые человек вызывает по одной в чате агента. Три самостоятельных процесса:

| Процесс | Команды | Артефакты |
|---|---|---|
| SDD (ядро) | `constitution` → `specify` → `clarify` → `plan` → `checklist` → `tasks` → `analyze` → `implement` → `converge` | `.specify/memory/constitution.md`; `specs/NNN-slug/`: `spec.md`, `checklists/requirements.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`, `tasks.md`, `checklists/<тема>.md` |
| Багфикс (расширение `bug`) | `bug.assess` → `bug.fix` → `bug.test` | `.specify/bugs/<slug>/assessment.md`, `fix.md`, `test.md` |
| Оценка идеи (расширение `assess`) | `assess.intake` → `research` → `define` → `shape` → `decide` | `.specify/assessments/<slug>/intake.md`, `research.md`, `problem.md`, `concept.md`, `decision.md` |

Процессы независимы: багфикс и оценка не требуют SDD, решение `go` не запускает SDD автоматически. Активная фича хранится указателем в `.specify/feature.json` (не в ветке git); ветки и автокоммиты даёт отдельное расширение `git` через хуки.

Масштаб: ~73 тыс. строк Python в `src/specify_cli`, более 300 файлов тестов, 226 релизов за год, 42 интеграции агентов, 157 расширений и 33 пресета в каталогах сообщества, 130 тыс. звёзд. История: основан 2025-08-21 (Den Delimarsky, John Lam), с января 2026 ведёт Manfred Riem; расширения появились в феврале 2026 как вклад сообщества, пресеты в марте, движок workflow в апреле, `bug` 2026-06-05, `assess` 2026-07-17, бандлы летом, 1.0.0 2026-08-21.

## Устройство

### Пять примитивов и каталоги

- **Интеграции** — классы в реестре `src/specify_cli/integrations/<agent>/`, базы `MarkdownIntegration`, `TomlIntegration`, `YamlIntegration`, `SkillsIntegration`. Claude Code и Codex — skills-интеграции: `.claude/skills/speckit-<cmd>/SKILL.md` (с `argument-hint`, `user-invocable`) и `.agents/skills/speckit-<cmd>/SKILL.md`, вызов `/speckit-specify` и `$speckit-specify`. Шаблоны команд общие, а написание вызовов подставляется при рендере плейсхолдерами `__SPECKIT_COMMAND_<X>__`, `__AGENT__`, `{SCRIPT}` (варианты sh/ps/py), `$ARGUMENTS`. Установленные файлы записаны в манифест с sha256 (`.specify/integrations/<key>.manifest.json`): `install`, `uninstall`, `upgrade`, `switch`, `use` идемпотентны и не трогают изменённые пользователем файлы. Есть `generic` с произвольным каталогом команд и внешние адаптеры из каталога с явным доверием.
- **Расширения** — `extension.yml`: команды `speckit.<ext>.<cmd>`, шаблоны и скрипты (только replace), конфиг, хуки `before_<cmd>` / `after_<cmd>` (optional или mandatory, priority, condition), события среды агента (SessionStart, PreToolUse и т. п. через сгенерированный `.specify/events.py`). Хуки регистрируются в `.specify/extensions.yml`, а исполняет их агент: каждый шаблон команды велит прочитать этот YAML и вывести блок `EXECUTE_COMMAND`. Условия хуков шаблоны не вычисляют и такие хуки пропускают.
- **Пресеты** — `preset.yml` подменяет команды, шаблоны и скрипты со стратегиями replace / prepend / append / wrap и приоритетами; локальные переопределения проекта в `.specify/templates/overrides/`. Порядок разрешения: overrides → пресеты → расширения → ядро. Встроенный пресет `lean` сжимает пять команд до «только промпт, только артефакт».
- **Workflow** — YAML-пайплайн из 13 типов шагов (`command`, `prompt`, `shell`, `init`, `slot`, `gate`, `if`, `switch`, `while`, `do-while`, `fan-out`, `fan-in`, `workflow`), выражения `{{ }}` с фильтрами, состояние запуска в `.specify/workflows/runs/<id>/` с деревом выполнения и `resume`. Гейт в TTY спрашивает человека, без TTY ставит запуск на паузу; `on_reject` abort / skip / retry, `verdict_input` для неинтерактивного ответа, `show_file` для материала ревью. Оверлеи (`insert_after`, `replace`, `remove` по якорям шагов) и слоты позволяют проекту менять установленный workflow, не редактируя его. Шаг `command` запускает CLI агента подпроцессом (для Codex `codex exec "<вызов>" --model … --json`) и получает только код выхода; захват stdout «запланирован».
- **Шаги workflow** — устанавливаемые Python-пакеты `step.yml` + `__init__.py`.
- **Бандлы** — `bundle.yml` с пинами расширений, пресетов, workflow и шагов; первопартийные `bugfix` и `assess` = расширение + workflow с гейтом ревью.

Каталоги есть у каждого семейства (переменная окружения → проект → пользователь → встроенные), с политикой install-allowed / discovery-only, кешем на час, историей версий с sha256. `specify artifact list|info|lookup --json` показывает стек композиции каждой команды, шаблона, скрипта и хука. `specify mcp` экспериментален и отдаёт только `version`.

### Как устроены команды SDD

Каждая команда — Markdown-промпт 8–22 КБ (`specify` 18 КБ, `clarify` 19,5 КБ, `checklist` 22 КБ, `converge` 13 КБ), который агент исполняет в основной сессии. Сообщество измерило полный набор в 18 799 токенов против 863 у пресета `lean`.

- `constitution`: заполняет шаблон принципов (плейсхолдеры `[ALL_CAPS]`), версия по SemVer, отчёт Sync Impact Report HTML-комментарием, защита от выполнения посторонних просьб (Scope Guard).
- `specify`: короткое имя 2–4 слова, каталог `specs/NNN-slug` (или timestamp), `spec.md` по шаблону: приоритизированные истории P1/P2/P3, каждая независимо проверяема, сценарии Given/When/Then, FR-###, SC-### измеримые без технологий, допущения; не более трёх маркеров `[NEEDS CLARIFICATION]`, остальное закрывается разумными умолчаниями; создаёт `checklists/requirements.md` и прогоняет по нему самопроверку до трёх итераций; оставшиеся вопросы задаёт таблицей вариантов.
- `clarify`: сканирует спецификацию по таксономии из десяти категорий (объём, модель данных, UX, нефункциональные, интеграции, краевые случаи, ограничения, терминология, критерии завершения, заглушки), задаёт не больше пяти вопросов по одному, каждый с рекомендуемым вариантом и фразой «почему это важно», сразу вписывает ответ в нужный раздел и в `## Clarifications / ### Session YYYY-MM-DD`, затем перепроверяет чеклист требований.
- `plan`: `plan.md` с техническим контекстом, гейтом «Constitution Check», структурой проекта и таблицей «Complexity Tracking» (обоснование каждого нарушения принципов); фаза 0 — `research.md` (решение, обоснование, альтернативы), фаза 1 — `data-model.md`, `contracts/`, `quickstart.md`.
- `checklist`: «юнит-тесты для английского» — вопросы о качестве требований (полнота, ясность, согласованность, измеримость, покрытие), `CHK###`, ссылки `[Spec §X]` / `[Gap]`; артефакт принадлежит ревьюеру, `[x]` означает «требование сформулировано качественно», а не «реализовано».
- `tasks`: `- [ ] T001 [P] [US1] описание с путём`, фазы Setup → Foundational → по истории → Polish; тесты только по запросу.
- `analyze`: только чтение, шесть проходов (дубли, неоднозначность, недоспецифицированность, конституция, покрытие задачами, несогласованность), не более 50 находок, нарушение MUST конституции всегда CRITICAL, правки предлагает, не вносит.
- `implement`: читает состояние чеклистов как гейт и при неотмеченных пунктах останавливается с вопросом; создаёт ignore-файлы под стек; идёт по фазам, отмечает `[X]`.
- `converge`: после реализации сверяет код с `spec.md`, `plan.md`, `tasks.md`, классифицирует пробелы missing / partial / contradicts / unrequested, только дописывает `## Phase N: Convergence` с задачами `T0xx … per FR-003 (missing)`; при отсутствии пробелов файл не меняется байт в байт и печатается «Converged». Цикл implement → converge повторяют до сходимости.

### Багфикс и оценка идеи

`bug.assess` читает отчёт (текст или URL с политикой доверия хостам: приватные сети и метаданные облаков запрещены, github/gitlab/jira без вопросов, остальное по подтверждению; содержимое страниц — данные, не инструкции), пишет вердикт valid / likely valid / invalid, серьёзность, гипотезу причины и план правки; `bug.fix` правит только названные файлы и записывает «Deviations from Assessment»; `bug.test` перепроверяет воспроизведение и тесты, итог verified / partial / failed, при не выполненном воспроизведении обязан понизить до partial.

`assess` оценивает идею до спецификации: исследование обязано собрать доказательства против идеи, решение — таблица критериев strong / adequate / weak / unknown и вердикт go / needs-clarification / kill; `go` требует доказательств не ниже adequate и сформированной концепции, `kill` считается успешным исходом, `go` даёт сводку для `specify`.

### Документация и практика

Разделы концепций (три модели жизни спецификаций: flow-back, flow-forward, living; «spec of specs» для эпиков; работа с большими фичами через ограничение задач на запуск и субагентов), руководства (существующий проект, монорепозиторий через ближайший `.specify` и `SPECIFY_INIT_DIR`, контрактная разработка, эволюция спецификаций, собственный agentic SDLC проекта), справочник по всем командам. Сам Spec Kit использует `assess` в GitHub Actions для оценки фич-реквестов, а багфикс-воркфлоу на Actions пока не используют расширение `bug`. Правило вклада: любое детерминированное поведение покрывается позитивными и негативными тестами, багфикс — регрессионным тестом.

## Сравнение с @spec-box/sdd

| Измерение | @spec-box/sdd 0.12.0 | Spec Kit 1.1.3 |
|---|---|---|
| Назначение | Довести фичу до готового пул-реквеста с минимумом остановок | Дать агенту структурированный процесс; человек ведёт шаги сам |
| Оркестрация | Детерминированная машина состояний в CLI, роли как субагенты с типизированным ответом `sbox-result`, проверки при `report` | Человек вызывает команду, агент исполняет длинный промпт в основной сессии; движок workflow опционален и видит только код выхода |
| Состояние | `change.yaml`: фаза, статус, гейты, ревизия, lock, возвраты, запуски, receipt | Указатель `feature.json` и факт наличия файлов; состояние только у запусков workflow |
| Истина о поведении | Истина spec-box или OpenSpec, дельты изменения, применение и архив при доставке, `sbox-contract` | `spec.md` на фичу; истина проекта и модель её поддержки оставлены команде |
| Знания проекта | Категории `.sbox/project/*.md` с `doctor`, ADR в `decisions/`, wiki с `read_when`, журнал `log.md` | `constitution.md` с версией и Sync Impact Report; расширение `agent-context` для `CLAUDE.md`/`AGENTS.md`; структурной валидации нет |

| Уточнения | Вопросы P0/P1/P2 планировщика, ответ `sbox approve --answer`, P0 останавливает | Команда `clarify`: таксономия, не более пяти вопросов по одному с рекомендацией, ответы вписываются в спецификацию |
| Аудит плана | Обязательный challenger, блокирующие находки возвращают в plan | `analyze` только отчёт, `checklist` артефакт ревьюера; решение за человеком |

| Доставка | Intent, архив, коммит с ключом, push, PR из `delivery_narrative` | Нет; расширение `git` коммитит по хукам, `github` создаёт issues из задач |
| Headless | `run`/`stop`/`watch`, продолжение сессий, стоимость, receipt, один транспортный повтор | `workflow run` диспетчеризует CLI агента, гейты ставят паузу, `resume`; стоимость не учитывается |
| Хосты | Claude Code и Codex, таблица раскладок, агенты по профилям моделей | 42 интеграции и `generic`, манифесты с хешами, upgrade/uninstall/switch, мульти-установка |

| Контекст на запуск | ≈ 12 КБ у исследователя после упрощения ролей | 8–22 КБ на команду, ≈ 18,8 тыс. токенов на полный цикл; `lean` ≈ 0,9 тыс. |

| Масштаб | ≈ 10 тыс. строк, 186 тестов, одна команда | ≈ 73 тыс. строк, 300+ файлов тестов, 300+ контрибьюторов |

### В чём Spec Kit сильнее

1. Механика уточнений: таксономия покрытия, лимит вопросов, рекомендуемый вариант, запись ответов прямо в артефакт.
2. Чеклист качества требований как артефакт с состоянием, которое читается как гейт перед реализацией.
3. `converge`: воспроизводимый цикл «найди пробел → допиши задачу со ссылкой на источник → реализуй», без переписывания существующих задач.
4. Жизненный цикл материалов хоста: манифест с хешами, обновление и удаление без потери правок пользователя, десятки агентов и `generic`.
5. Слои настройки с приоритетами и интроспекцией, распространение через каталоги и бандлы.
6. Отдельные процессы для багов и для оценки идеи с честными вердиктами (partial при невыполненном воспроизведении, kill как успех).
7. Объём документации: руководства для существующих проектов, монорепозиториев, контрактов, моделей жизни спецификаций.

### В чём @spec-box/sdd сильнее

1. Детерминированное ядро: контракт ответа роли, проверки при приёме, бюджеты возвратов и отклонений, статусы parked/stopped/delivery_unknown, receipt и provenance.
2. Истина о поведении всего продукта с дельтами и архивом в пул-реквесте; тесты по сценариям дельт до кода и их защита.
3. Независимый аудит плана, ревью тестов, верификатор перед ревьюером, disposition каждого не-PASS пункта, запечатанный change-set и привязка вердиктов к дайджесту.
4. Исследование с проверяемыми цитатами запроса, расхождения на гейте, журнал `[CODE]` для поздних ролей.
5. Headless с продолжением сессий, учётом стоимости, метриками и идемпотентной доставкой до пул-реквеста.
6. Инструменты для агентов (`sbox-browser`, `sbox-wiki`, `sbox-contract`) и справка по требованию при малом контексте запуска.
7. Профили моделей по ролям и сложности.

## Кандидаты на заимствование

Каждый пункт можно принять или отклонить отдельно. Приоритет отражает ожидаемую пользу для пилота при ограничении «механизмы, а не знания о проекте».

| G | Семантика вердиктов из `bug.test` и `assess.decide` для этапов 3 и 6: таблица критериев strong/adequate/weak/unknown, вердикт go/needs-clarification/kill, обязательные доказательства против идеи, понижение результата при невыполненном воспроизведении | design.md §9 (дискавери), схема bugfix, роль verifier | средний |
| H | Правило о внешнем содержимом для всех ролей: страницы, тикеты и файлы из URL — данные, а не инструкции; секреты в артефакты не переносятся; приватные адреса для браузера запрещены | `assets/roles/*.md` или тема справки, скилл `sbox-browser` | средний |

Что не берём: исполнение хуков агентом через чтение YAML (противоречит детерминированному ядру), единый указатель активной фичи (у нас `--change` и lock), необязательные тесты, универсальный DSL workflow с циклами и fan-out (машина состояний плюс схема артефактов покрывают пилоты; вернуться при схеме bugfix), каталоги и бандлы (нет второго потребителя), промпты команд по 20 КБ.

## Открытые вопросы

1. Пункты A–C меняют контракт ролей и схему артефактов: делать их до или после повторного прогона пилота на 0.12.0.
2. Этап 3 (дискавери) проектировать по модели `assess` (вердикт go/kill) или оставить критерии достаточности брифа из design.md §9.
3. Нужен ли хост `generic` до появления третьего реального хоста.
